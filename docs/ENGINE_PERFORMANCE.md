# 实验引擎逐键性能测量

后续进度：[多进程共享引擎对照](ENGINE_IPC_PERFORMANCE.md)已提供真实独立客户端的 local／isolated／shared 三模式、1／2／4 人数测量，区分完整管道往返与本地查询，按同轮采样求总私有内存。本页以下记录此前进程内分阶段测量，不能直接与新口径作数值对照。

WIN-03b／CN-02，2026-11-10。新增 harukoto_engine_benchmark 与 scripts/benchmark-engine.py，测量[Windows 合并查询](ENGINE_WINDOWS.md)每一次实际按键的核心重建、SQLite 打开、候选合并和[单工作线程](ENGINE_EXECUTOR.md)往返，不把此前“中间按键返回空候选”的功能测试当逐键性能。

## 运行方法

使用已配置完整词库的 MSVC Release 构建，然后通过 Python 运行。整个过程在临时目录制作基础快照并导入 FF14，不改安装、注册或用户词库：

```powershell
python -X utf8 scripts/benchmark-engine.py --reader .build/windows/msvc/Release/harukoto_engine_benchmark.exe --lexicon .build/windows/ime --runs 3 --output .build/windows/engine-performance.json
```

先基础场景、再 FF14 全量开启；每个场景先 direct、再 executor，各为独立进程。direct 在服务端所属线程直接计算，executor 使用一个工作线程和一个槽位；均逐个发键并等待该键完整回复，不模拟快速连续输入、多连接竞争或管道 I/O。每次请求都经过 ServerConnection 接受／完成校验，executor 另含提交、线程唤醒、查询包复验和结果领取。

固定样本为 nihao、xinkule、riben、eat、nihaoz；FF14 场景增加 tejihuifuyao。每轮基础 26 键、FF14 38 键，三轮四组共 384 个逐键样本、66 次实际选择。每段输入最后验证“你好／辛苦了／日本／食べる／特级恢复药”，nihaoz 只消费 nihao、保留 z；重复 Select 必须返回原回复而不再消费。选词和重复请求验证在计时区间之外。

## 记录与解释

查询分阶段计时是 WindowsDictionary.query 的可选参数；常规查询不读这些阶段时钟，也不改变候选计算和顺序。失败查询不输出成功样本。字段均为毫秒：

| 字段 | 包含内容 |
| --- | --- |
| setup_ms | 输入检查、创建独立核心会话、设置简繁与片段上下文 |
| replay_ms | 从空会话逐字恢复完整输入；每次 mpn_key 可能重新解码前缀 |
| sqlite_open_ms | 加载系统 SQLite、只读打开数据库、检测表结构与准备查询 |
| merge_ms | 首轮正式 Windows 候选合并，含 SQLite 查词与来源处理 |
| expansion_ms | 至多三轮核心候选扩展与正式追加合并 |
| conversion_ms | 整理候选 ID／正文／注释、按页截取及完整包校验 |
| cleanup_ms | queryImpl 返回后的剩余耗时，主要为局部对象／SQLite／核心会话释放，也含计时包装开销 |
| total_ms | 完整查询调用，含清理 |
| request_ms | 从服务端接受当前 Key 前到完成回复后，含查询和相应直调／后台调度 |

cleanup_ms 是总时长减去各显式阶段后的余量，并非单独挂钩析构采样。其余阶段时钟也有开销；不应用微小差值判断优化。request_ms 不包括外部键盘事件、真实 IPC、TSF 写锁、宿主插入、候选窗口绘制。

每组记录全部原始样本及中位／最大／合计。不同长度和输入类型混在组内，组中位数只用于总览；应同时按 case、key 和 run 查原始数据。少量轮次不报告 P95／P99。load_ms 单独记录完整词库准备，包含清单／SHA256／SQLite 完整性校验和合并复制，不混入逐键请求。

报告保存 Git 提交与 source_dirty、相关源码和测量程序 SHA256、基础四文件大小／SHA256、FF14 清单和词表哈希、系统版本。结束复核程序、源码和词库未改变。只使用固定测试文本，不记录用户输入、机器名、用户路径或安装状态。报告脚本严格拒绝缺键、重复样本、缺选择验证、非有限／负数时间和阶段合计不一致；失败不写新的成功报告。

## 验证和后续

engine_benchmark 使用微型基础词库配合真实 FF14 主题，跑四个进程／128 次实际逐键查询和 22 次选择验证，同时检查源文件不变、哈希、汇总与坏报告拒绝。初次测试发现 Windows 文本写入将固定 LF 容器头转为 CRLF；测试制作器已显式保持 LF，修复后通过。完整构建与 engine_executor、engine_windows_full、engine_benchmark 三项相关测试通过；未为本批重复运行全部 38 项。

## 完整词库基线

从干净提交 cadd221 运行三轮：[原始报告](benchmarks/engine-query-baseline.json)。384 个逐键样本、66 次选词验证全部通过，源码／程序／词库前后哈希一致，source_dirty=false。未与构建或 CTest 并行，未清空磁盘缓存或控制系统其他负载。三轮每组仅有每段固定输入的不同前缀，不是相互独立的大样本。

| 场景／方式 | 样本 | 请求中位／最大 ms | 查询合计 ms | 重建／SQLite／合并／扩展合计 ms |
| --- | --- | --- | --- | --- |
| 基础 direct | 78 | 1.95／11.91 | 284.84 | 21.30／37.58／14.52／207.54 |
| 基础 executor | 78 | 2.03／13.55 | 288.64 | 21.27／37.86／14.66／210.99 |
| FF14 direct | 114 | 7.80／63.10 | 1593.31 | 84.54／53.79／178.68／1270.67 |
| FF14 executor | 114 | 7.93／66.82 | 1621.67 | 86.98／56.62／182.29／1289.54 |

准备词库分别约 1.05～1.07 秒（基础）与 1.48～1.52 秒（FF14），含校验与完整合并，不是逐键成本。FF14 的扩展阶段约占查询合计 80%，SQLite 打开约 3.4%；基础场景分别约 73%／13%。扩展包含原生搜索及多轮 Windows 合并，不能单凭此表把全部扩展时间归给某一函数。

代码检查发现每轮 windowsCandidates 都重扫整张日语／主题表，并在 mixedReading 中重建读音映射。下一步优先建立快照内不可变读音索引，按当前完整触发和可能的混打子串准备同序词条视图，扩展复用该视图；必须逐项对照原正式合并的正文、消费、注释和顺序。再以同一程序／样本做前后对照，之后才决定 SQLite 复用或核心状态重建优化。当前没有降低搜索预算，不宣称内存已有改善；冷缓存、并发会话、真实应用和多进程共享收益仍需单独测量。

## 读音索引实现

基线后的第一项优化已实现：快照建立完整 reading→原词表位置索引，查询只复制完整触发及受现有规则约束的混打子串，三轮候选扩展复用视图。原生重建、SQLite 打开／查词、搜索次数和正式合并算法均未替换；变化范围见[合并适配器](ENGINE_WINDOWS.md)。

完整构建及三项相关 CTest 通过：执行器 0.02 秒、测量工具 5.61 秒、扩大的全量合并对照 16.36 秒（修正受控测试词的容器格式后）。只更新实验查询，未运行其余既有测试。下一步从干净的索引实现提交再次跑三轮，核对四文件／FF14／驱动脚本指纹及样本一致，再记录前后差异。

## 索引后的同条件对照

干净提交 42458d7 的[原始报告](benchmarks/engine-query-indexed.json)同样有 384 次逐键查询和 66 次实际选择验证。与基线逐项核对场景／方式／case／轮次／键位置完全一致；基础四文件、FF14、驱动 C++、Python 脚本与其余记录源码哈希一致，只有 Windows/EngineWindows.h 改变；重编后程序哈希相应改变，两份均 source_dirty=false。

| 场景／方式 | 请求中位／最大 ms | 查询合计 ms | 重建／SQLite／合并／扩展合计 ms |
| --- | --- | --- | --- |
| 基础 direct | 1.79／11.67 | 267.67 | 20.26／35.86／13.01／194.83 |
| 基础 executor | 1.86／12.05 | 275.31 | 20.84／37.51／13.38／199.50 |
| FF14 direct | 1.98／56.13 | 916.71 | 83.74／51.89／17.25／759.01 |
| FF14 executor | 2.36／56.89 | 948.88 | 87.91／56.11／18.62／781.19 |

本机固定样本下，FF14 后台请求中位由 7.93 降至 2.36 ms（约 70%），完整查询合计下降约 41.5%，首轮合并合计由 182.29 降至 18.62 ms，扩展合计由 1289.54 降至 781.19 ms。最大请求仍为 56.89 ms，部分较长前缀的搜索成本没有消失。基础场景差异较小，不能用三轮顺序运行的小差值宣称普遍提速。

准备耗时仍约 1.03～1.06 秒（基础）与 1.49～1.52 秒（FF14），未对索引额外内存作测量。测量顺序、计时开销、缓存与系统负载限制与基线相同，结果仅说明实验查询的这组样本有所改善，不是正式输入法、实际游戏、多会话竞争或屏幕延迟验收。

目前优先热点已缩小到剩余核心搜索和扩展；不据此引入复杂 SQLite 连接池。共享引擎路线接下来进入当前用户认证管道与独立进程生命周期，保留 CN-02 的长前缀／队列竞争／内存跟踪，最后与真实 TSF 路径一并验收。
