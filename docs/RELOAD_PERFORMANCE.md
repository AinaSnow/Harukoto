# 热更新性能测量

WIN-03／CN-02：用独立进程调用实际 Service::pollDictionaries，测量基础快照初次加载、更新、回退和无变化检查。每个进程有一个活动上下文和一个挂起上下文，保留两者待上屏队列；基础中文与 FF14 全量开启分开测，各重复三轮。支持单进程与多个进程共享仓库同时更新。测试运行在临时仓库，不改用户安装、注册或词库配置。

## 复现

先用 MSVC Release 构建 Windows 工程，再在仓库根目录用 PowerShell 7 执行：

~~~powershell
python -X utf8 scripts/benchmark-reload.py --reader .build/windows/msvc/Release/harukoto_service_reload_test.exe --lexicon .build/windows/ime --runs 3 --output .build/windows/reload-performance.json
~~~

工具使用同一份四文件内容生成两个不同版本标识，通过正式 Python 发布／回退工具切换。每次测量后在计时区间之外检查“你好”可选并提交。报告记录源码提交、是否含未提交修改、测试程序 SHA256、四文件大小／SHA256、FF14 清单／词表哈希和系统版本，不保存机器名、用户路径或实际输入内容。

initial 表示测试服务从安装基础词库首次采用用户快照；FF14 场景也在该次首次合并主题，不能当成“启动时已经加载 FF14”的实机首次更新。update 和 rollback 才是已有 FF14 合并表时再次更换基础快照。两代数据内容相同，测的是重建与释放流程，不衡量词库增量大小或质量变化。

## 指标边界

| 字段 | 含义 |
| --- | --- |
| dispatch_ms | TSF 所属线程启动后台检查的耗时 |
| background_wait_ms | 启动之后等待后台完成的墙钟时间，含调度和采样开销，非纯工作线程 CPU 时间 |
| apply_ms | 所属线程执行发布的耗时，含会话替换、状态报告；优化前含同步旧数据析构，优化后含清理任务启动 |
| private_before／ready／after | 操作前、后台准备完成、前台发布返回后的进程私有内存字节数 |
| sampled_peak_private | 等待阶段约 1 ms 采样及几个边界点的最大私有内存，不是严格峰值 |
| cleanup_wait_ms／private_settled | 优化后额外等待清理完成的时间与之后的私有内存；前台不执行这个测试等待 |

文件在测量前已经复制和哈希，磁盘缓存未清空，因此这是缓存通常已热的本机测量。每组只有三轮，报告中位数和最大值，不用三轮结果宣称 P95／P99。没有输入应用的实际 TSF 写锁、宿主插入、候选窗口 IPC 或绘制；不能将 apply_ms 当成按键到屏幕延迟。alpha.21／22 前后对照是单进程，新增并发对照见下文。

测试程序在准备初始词库后释放读文件的临时字符串，避免比真实 Activate 多保留一份大缓冲区。后台准备新版本时新旧数据同时存在是预期行为；异步清理后 private_after 可能仍包含旧版，需与 private_settled 分开看。堆分配器可能保留已释放内存，私有字节数不等于活跃词条对象总大小。

## alpha.22 优化范围

本机 2026-11-10 对照：[优化前原始报告](benchmarks/reload-alpha21-before.json)、[优化后原始报告](benchmarks/reload-alpha22-after.json)。两次都基于 cceddb5 加工作区改动，source_dirty=true；前者只加测试测量入口，后者包含后台清理改动，测试程序 SHA256 不同。报告中的版本名是对照标签，不表示干净发行制品；最终打包提交另记开发状态。两次基准顺序执行，未与 CTest／构建并行；系统其他负载和缓存仍未受控。

| 场景 | 优化前 apply 中位／最大 ms | 优化后 apply 中位／最大 ms |
| --- | --- | --- |
| 基础：首次采用用户快照 | 27.168／28.381 | 0.151／0.154 |
| 基础：更新 | 27.799／34.143 | 0.072／0.073 |
| 基础：回退 | 30.983／33.496 | 0.071／0.077 |
| FF14：首次采用用户快照 | 26.131／29.502 | 0.178／0.241 |
| FF14：更新 | 49.012／53.591 | 0.074／0.092 |
| FF14：回退 | 44.157／50.827 | 0.098／0.105 |

优化后，更新时后台等待中位约为基础 1176 ms、FF14 1534 ms；后台清理等待中位分别为 31.2 ms、46.6 ms。清理成本被移出了前台路径，并没有消失。FF14 更新采样内存最大值前后约为 352.8／352.6 MiB，不能据此宣称降低峰值；优化后发布刚返回时仍约 304.1 MiB，清理结束后中位约 157.5 MiB。无变化发布中位约 0.01 ms。原始两份报告保留全部 24 个样本和哈希，精确值以 JSON 为准。

首次测量定位到前台发布后的旧快照、原始安装词库及 FF14 合并词表析构。现在将持有旧数据的任务交给独立清理线程；它持有 DLL 引用和独立对象，不访问 Service 或 COM。当前上下文和挂起上下文已经换好会话后才允许清理旧数据。清理线程创建失败时保留旧对象，后续按键重试，并暂缓新任务，避免在输入路径同步释放。

无变化检查不启动额外清理线程。诊断阶段不因清理工作改成“加载中”，失败标志也不被清理完成覆盖。服务退出不等待已启动的清理工作；未能交出的残留数据仍由服务析构释放。会话析构和初始 SQLite 连接关闭仍在前台，不宣称整个发布路径零分配或严格无停顿。

## alpha.22 多进程并发对照

2026-11-10 从干净提交 80848c2 运行基准，支持 `--hosts 1～8`，默认 1。本批依次测 1、2、4 个独立服务测试进程，每种规模纯基础／FF14 各三轮，包含 initial／update／rollback／unchanged，共 168 个进程操作样本、72 个并发组。每次操作后逐进程检查“你好”选词提交。另有三进程小词库回归用不同词条验证更新／回退确实改变候选，并验证采样失败会报错及释放采样句柄。

~~~powershell
foreach ($hostCount in @(1,2,4)) {
    python -X utf8 scripts/benchmark-reload.py --reader .build/windows/msvc/Release/harukoto_service_reload_test.exe --lexicon .build/windows/ime --runs 3 --hosts $hostCount --output ".build/windows/reload-concurrent-$hostCount.json"
    if ($LASTEXITCODE -ne 0) { throw '并发测量失败' }
}
~~~

各进程先初始化，读取同一临时仓库；每次正式发布完成后，控制线程通过屏障一起发送 measure。所有进程完成本次测量（含清理等待）后才进行选词检查及下一次发布。没有真实应用，也没有安装新版输入法；本批只扩展测试工具，运行时代码及 alpha.22 安装包保持不变。

原始报告：[1 个进程](benchmarks/reload-alpha22-hosts1.json)、[2 个进程](benchmarks/reload-alpha22-hosts2.json)、[4 个进程](benchmarks/reload-alpha22-hosts4.json)。三份 format=2 报告的测试程序／脚本／基础四文件／FF14 哈希一致，source_dirty=false。每份 summary 按场景／操作汇总所有进程样本，4 进程时每行 12 个样本来自 3 轮，不能当成 12 次相互独立实验；groups 保留每一轮整体测量。

下表只比较 update，清理后内存取三轮中位，采样峰值取三轮最大：

| 场景／进程数 | 每进程 apply 中位／最大 ms | 每进程后台等待中位 ms | 整组完成中位 ms | 合计采样峰值 MiB | 合计清理后 MiB |
| --- | --- | --- | --- | --- | --- |
| 基础／1 | 0.079／0.082 | 1150.6 | 1181.9 | 275.0 | 121.7 |
| 基础／2 | 0.060／0.066 | 1421.7 | 1456.9 | 548.7 | 243.4 |
| 基础／4 | 0.075／0.095 | 1532.1 | 1565.9 | 1096.7 | 486.6 |
| FF14／1 | 0.075／0.093 | 1728.7 | 1790.8 | 349.6 | 156.3 |
| FF14／2 | 0.085／0.097 | 2093.2 | 2159.3 | 705.4 | 313.8 |
| FF14／4 | 0.100／0.143 | 2257.3 | 2333.0 | 1398.3 | 626.1 |

新增指标：

| groups 字段 | 含义与限制 |
| --- | --- |
| command_start_spread_ms | Python 各线程发命令前时间点的最大差；不是原生后台真正开始的时间差 |
| group_wall_ms | 从释放屏障到全部 measure 回复，包含后台、发布、清理等待与管道开销；不包含词库发布和选词检查 |
| aggregate_private_before／settled | 同一轮遍历读取各进程私有字节并求和；不包含控制进程和文件缓存，不是物理驻留内存 |
| aggregate_sampled_peak_private | 每轮求和后取最大值，不能用各进程独立峰值之和替代；请求采样间隔 5 ms，系统调度可能延长 |
| aggregate_samples／max_sample_sweep_ms | 实际采样轮数及遍历一轮的最长耗时；读取不是原子操作，峰值是近似采样结果 |

4 进程所有阶段最大命令发送差约 0.115 ms，最长采样遍历约 1.294 ms。整体采样覆盖命令发送前到全部清理完成，补上了单进程原生采样未连续覆盖前台发布／清理的阶段，但仍不能声称严格瞬时峰值。测量包含采样开销；未清空系统缓存，未控制其他系统负载，各规模按顺序运行，不能用小数点差异断言优化或退化。

本批未观察到版本错误、更新／回退后的选词失败。前台切换仍较短，但后台等待随并发增加；四进程 FF14 合计采样峰值约 1.37 GiB，清理后约 626 MiB，说明每个宿主各自持有词库的内存成本仍在。这支持 WIN-03b 优先验证“单用户引擎共享只读词库、会话状态隔离”，不是已经实现了共享或证明其延迟可接受。

下一步保留冷缓存、更多挂起上下文、大个人表、实机 TSF 投递和按键到候选显示验收；独立引擎先明确协议与会话隔离，再用同条件测量比较内存和请求延迟。
