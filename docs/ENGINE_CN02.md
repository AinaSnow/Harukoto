# 独立引擎真实延迟与内存对比（WIN-03 第 8 步 / CN-02）

WIN-03 阶段二第 8 步（CN-02），2026-11-23。在真实生产 `TextService`（`Windows/TextService.cpp`）、真实 Explorer 启动的常驻所有者与独立多子进程条件下，全面对比「独立引擎（瘦客户端，协议 v2）」与「进程内路径」的冷／热启动、逐键到候选可见延迟、深页翻页、大个人表与学习重载、多应用并发输入及总内存，并据此发现并修复了独立引擎首页提前执行 3 轮候选扩展的严重延迟回退。

## 1. 方法与测量边界

工具：`harukoto_engine_cn02_benchmark`（`Windows/tests/EngineCn02Benchmark.cpp`）＋ `scripts/benchmark-cn02.py`。每个客户端都是独立的 Windows 子进程，直接驱动生产 `Service` 类（进程内模式完整加载基础快照＋FF14 0.4.0＋SQLite＋个人表；引擎模式以 35 字节占位词库瘦客户端启动，经 `tsf_engine::Link::threaded`＋真实发现／交接／命名管道连向常驻进程 `harukoto_engine_owner_test.exe`＋`harukoto_engine_host.exe`）。不修改 HKLM 或已安装的输入法，结束时清理全部测试进程、HKCU 测试键与临时目录。

- **双运行模式**：
  - `--mode resident`（正式模式，需普通权限 Medium IL PowerShell）：复制 `harukoto_engine_owner_test.exe` 与 `harukoto_engine_host.exe` 到临时版本目录，写 HKCU 测试键，由真实 Explorer 按需拉起常驻所有者，覆盖真实冷启动与热握手。
  - `--mode direct`（直连模式，可在提权环境复现）：由主进程经 `EngineProcess` 启动真实 8 线程 `harukoto_engine_host.exe` 并向各子进程分配独立管道端点，跳过 Explorer 冷启动，其余全部指标与 `resident` 路径相同。
- **计入的端到端环节**：
  - 逐键：`mpn_key()` → `refreshCandidates()` →（引擎模式：`engineSettings()`、工作线程 IPC 往返、`harukoto_engine_host.exe` 8 线程查询、通知事件唤醒、`deliverEngine()`、`materialize()`、`mergeQuickCandidates()`；进程内模式：本地核心解码、`windowsCandidates()`、SQLite 查询、合并）→ 首页 7 项可见文本／读音／纠错标记拼装（与 `updatePopup()` 一致）。
  - 选词：`chooseCandidate(0, text, learn)`（引擎模式走协议 v2 无状态 `KeyAction::Inspect`）。
  - 深页：10 个高扩展读音（`shi`、`yi`、`ji`、`li`、`zhi`、`zhongguo`、`wozaiditieshang`、`xianzai`、`wenti`、`keyi`），反复翻页并触发 `expandCandidates()` 直到 3 轮耗尽，逐条校验候选总数、页数与全部文本 FNV-1a 哈希一致。
  - 大个人表：合成 **5,000 条个人日语词**（`japanese-custom.tsv`）＋ **5,000 条选词记忆**（`selection-memory.tsv`）＋ **5,000 条个人词频**（`selection-memory-words.tsv`）＋ **1,000 条手动个人中文词**（`selection-memory-user.tsv`），测加载耗时、内存、63 组稳态逐键，以及 10 轮“选词学习落盘（`remember`＋`flush`）后立刻输入下一词首键触发引擎重载”的延迟。
- **未计入（留待实机）**：TSF 编辑会话调度、`WM_COPYDATA` 到 `MeowpuutGlassPreview.exe` 与图形帧渲染、冷磁盘缓存（系统文件缓存已热）、低配 CPU、真实应用内体感。
- **语料与数据**：仓库生产词库（`.build/windows/ime`，410,625 条基础中文）＋ FF14 0.4.0（60,491 条主题词）；逐键语料与第 5 步一致，共 3,464 键（`tuned`＋`holdout`＋`words-dev`＋3 条 FF14，饱和连续输入无思考间隔；不输出任何 `holdout` 明文）。
- **正式测量环境与原始报告**：Windows 11 10.0.26300，16 逻辑 CPU，MSVC Release 静态运行时，普通权限（Medium IL）PowerShell 执行；原始归档：[engine-cn02-win03-8.json](benchmarks/engine-cn02-win03-8.json)（78.3 KiB，含全部汇总与事件，`dirty=true` 为提交前实测）。

## 2. 本批发现并修复的关键性能问题：首页按轮次严格懒扩展

首轮 CN-02 基准直接暴露了一个此前未被单元测试察觉的严重瓶颈：
- **根因**：第 6c 步将 TSF 扩展查询页大小定为 `QueryPageSize = 128`，而 `WindowsDictionary::queryImpl()` 为填满一页（`required = start + 128 + 1`），在第 0 轮候选不足 129 条时对**每一次按键**都提前跑完了全部 3 轮 `mpn_expand_candidates()`＋`windowsCandidates()`；进程内路径只在用户真正按 `PageDown` 时才扩展。
- **修复**（`Windows/EngineWindows.h`、`Windows/EngineTsf.h`、`Windows/TextService.cpp`，协议版本维持 v2 不变）：当 `work.key.extended == true` 时改为**按轮次严格懒扩展分页**——第 0 轮独占页区间 `[0, p0)`，在 `work.page < p0` 上**绝不调用 `mpn_expand_candidates()`**，仅在非空首页以 `page.more` 告知是否可继续扩展（遵守空页不得带 `more` 的协议约束）；第 1～3 轮各占独立页段，严格在客户端发 `PageNext` 时只扩展到命中的那一轮即停，避免在全 11 组模糊音长句上首次翻页就跨轮跑完第 3 轮触发 1 秒超时。客户端 `Driver::fetch()`／`fetchMore()` 补充 `roundComplete` 标记，收到短页即确认当轮完整、不再多发 `PageNext`。
- **修复前后实测对比（单客户端，3,464 键全语料＋FF14，同机 `direct` 模式对照）**：

| 指标 | 进程内路径 | 独立引擎（修复前） | **独立引擎（修复后）** | 修复幅度 |
| --- | --- | --- | --- | --- |
| 3,464 键总墙钟时间 | 11,936 ms | 75,540 ms | **5,665 ms** | **快 13.3×**（且比进程内快 2.1×） |
| 逐键中位 / p95 / p99 | 3.07 / 6.42 / 8.55 ms | 5.79 / 101.40 / 248.66 ms | **1.29 / 4.41 / 6.08 ms** | p95 **快 23.0×**、p99 **快 40.9×** |
| 逐键最大值 | 12.90 ms | 465.73 ms | **9.76 ms** | **快 47.7×** |
| 17+ 键长句中位 / 最大 | 6.55 / 12.90 ms | 68.20 / 465.73 ms | **4.17 / 9.76 ms** | **快 16.4× / 47.7×** |
| 5,000 词大个人表稳态逐键中位 / 最大 | 3.43 / 8.24 ms | 15.06 / 106.11 ms | **2.73 / 7.65 ms** | **快 5.5× / 13.9×** |

修复后独立引擎在单客户端与多客户端下**全面快于进程内路径**，主要因为宿主对 60,491 条 FF14＋个人日语词维护了 `readings_` 哈希索引（O(1) 查找），而进程内路径每键线性扫描全量日语词表。

## 4. 默认开启条件评估

对照 [开发计划](DEVELOPMENT_PLAN.md#阶段二独立引擎win-03) 规定的三条默认开启门槛：

1. **WIN-03 第 1～8 步自动测试全部通过**：**已达成**——普通权限（Medium IL）PowerShell 全量 **69 / 69 项 CTest 100% 通过**（1,884.98 秒，含 `engine_discovery`、`engine_handoff`、`engine_resident`、`engine_cost_benchmark`、`engine_tsf_full` 全量 8 场景 31,056 列表瘦客户端 0 不一致对照、及新增 `engine_cn02_benchmark`）。
2. **CN-02 延迟与内存对比可接受**：**已达成且全面优于进程内**——冷启动快 0.95 秒（2.39 s vs 3.35 s）、次应用热启动快 458×（7.30 ms vs 3,346 ms）、单／多应用逐键快 2.0×～8.2×（1.51～3.61 ms vs 3.74～29.51 ms）、12 应用总内存节省 88.2%（238.8 MiB vs 2,030.1 MiB，省约 1.75 GiB）、深页 100% 一致且更快、大个人表稳态快 34%、全程 0 回退。
3. **VAL-01 实机清单在开启状态下走通**：**待实机**（需将第 8 步首页去提前扩展优化打入下一版试用包，在记事本、QQ、FF14 按 [WINDOWS_VALIDATION.md](WINDOWS_VALIDATION.md) 走通并留证）。

因此当前仍保持 `StandaloneEngine` 默认关闭；待下一版试用包在实机走通 VAL-01 清单后，即满足默认开启独立引擎的全部条件。
