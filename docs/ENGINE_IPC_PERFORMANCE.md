# 多进程共享引擎的延迟与内存对照

WIN-03b／CN-02，2026-11-10。`harukoto_engine_ipc_benchmark` 与 `scripts/benchmark-engine-ipc.py` 使用真实独立客户端进程，比较固定词库的进程内查询、独占宿主与共享宿主。基于[受控启动](ENGINE_PROCESS.md)和[查询宿主](ENGINE_HOST.md)，不接 TSF、候选窗或实际应用，不改安装、注册和用户词库。发行保持 alpha.22。

## 对照口径

| 模式 | 进程组成 | 查询与调度 |
| --- | --- | --- |
| local | 1 个协调进程＋N 个客户端，每客户端加载一份 WindowsDictionary | ClientGate／ServerConnection 与正式合并查询在客户端线程执行，无管道或后台执行器 |
| isolated | 1 个协调进程＋N 个客户端＋N 个宿主 | 每客户端独占宿主；每宿主 2 工作线程、32 槽，实际管道往返 |
| shared | 1 个协调进程＋N 个客户端＋1 个宿主 | N 个连接共用一份词库、2 工作线程和32 槽，实际管道往返 |

N 为 1／2／4。local 是冻结实验词库的本地查询基线，不是当前已安装 TSF DLL 的实现或内存模型；isolated／shared 除宿主数量和端点分配外使用同一程序与默认配置。shared 与 isolated 的总工作线程数不同，因此不能把延迟差全部归因于 IPC 或共享词库。静态代码页、系统文件缓存和 Windows 的共享映射不重复计入私有提交。

每组在所有客户端完成词库准备／管道握手后，以同一个手动事件放行。各客户端逐键发送，收到并验证完整候选后才发下一键，每连接至多一个请求；这是不带人工间隔的竞争负载。记录 QPC 放行计数、各客户端开始／完成计数和频率，汇总实际唤醒时间差及全员工作区间的共同重叠；不能把事件放行等同于完全同时发送，也不能把工作区间重叠当作每次请求都同时排队。

固定 nihao、xinkule、riben、eat、nihaoz，FF14 场景另加 tejihuifuyao。每轮每客户端基础 26 键、FF14 38 键；完整默认矩阵为两场景×三种人数×三模式×三轮，共 4,032 个逐键样本、693 次实际选择验证。验证最终“你好／辛苦了／日本／食べる／特级恢复药”，nihaoz 选择后保留 z；每次候选检查输入前缀及 ClientGate／快照归属。该工具不逐页对照完整候选，相关字节对照与重复选择继续由 engine_host_process／full 覆盖。

## 时延与内存字段

request_ms 从客户端创建当前 Key 前计时，到完整候选经解码、归属验证和保存后结束；远程模式包括编码、管道收发、服务端调度／排队、完整查询和客户端处理。local 保留消息／候选验证与载荷转换，但没有线上帧和传输层。取消、最终选择和报告写入不计入逐键时间。wall_ms 是放行到全部客户端完成报告并发出 done 的墙钟区间，包含取消／选择和输出，不是各键时间之和。

prepare_ms 从协调器创建事件前至全部客户端就绪，包含引擎加载、客户端启动和握手；多个独占宿主顺序启动，本地客户端则可同时加载，不能拿该字段当相同启动调度下的性能对照。每个客户端先在内存保存固定样本，结束后写临时报告，不在每个键之间刷新输出。

内存只测所有进程已就绪到工作结束且仍保留连接／词库的阶段，不覆盖加载期间峰值。调用 GetProcessMemoryInfo 的 PrivateUsage，单位字节，表示私有提交量，不是物理驻留内存或 Windows 总占用。每轮依次读取协调器、所有客户端和宿主，再对本轮求和；不相加不同进程各自的历史峰值。报告含：

- ready：全部就绪但尚未放行时的一轮采样。
- sampled_peak：ready、竞争期间和 held 各轮总量中的最大值，以及同一轮的角色分项。
- held：全部客户端完成查询和写报告、尚未释放词库／通道时的一轮采样。
- samples／interval_ms／max_sweep_ms：采样次数、竞争期请求等待 10 ms 的间隔和最大单轮读取耗时；事件可使等待提前结束，系统调度也可能延后，不能保证实际间隔恰好为 10 ms。采样不是原子快照，会遗漏短暂峰值；采样开销和系统调度也会影响请求时间。

协调器不加载对照词库，私有内存也纳入总量。全部客户端在 held 后才获准退出，宿主实际退出码须为 0 才输出成功组记录。工作进程使用只继承控制事件／可信引擎进程对象的句柄列表和自有 kill-on-close Job；协调器异常结束时只回收自己创建的进程。引擎端点通过 takeEndpoint 一次性领取，只传递 query／wait 权限的保留进程对象，不从公开 PID 重新建立信任。它是测试启动方的显式交接，不是正式多应用服务发现。

## 复现与报告校验

使用 PowerShell 7，已有完整基础词库时：

```powershell
cmake --build .build/windows/msvc --config Release
python -X utf8 scripts/benchmark-engine-ipc.py --reader .build/windows/msvc/Release/harukoto_engine_ipc_benchmark.exe --host .build/windows/msvc/Release/harukoto_engine_host.exe --lexicon .build/windows/ime --runs 3 --output .build/windows/engine-ipc-performance.json
```

脚本在临时目录制作基础快照和完整 FF14，顺序按基础／FF14、1／2／4 人数、local／isolated／shared 运行。重复共享文件与此固定顺序会受缓存影响；没有清磁盘缓存、绑核、固定 CPU 频率或控制其他系统负载。少量固定前缀的多轮数据不视作独立大样本，仅报告中位、最大、合计，不发布 P95／P99 或真实游戏延迟结论。

报告记录 Git 提交、source_dirty、相关源码及两个程序 SHA256、基础四文件大小／哈希、FF14 文件哈希、系统版本与逻辑 CPU 数。结束复核程序、源码及词库身份不变；只记录固定测试文本，不包含用户输入、机器名、用户路径或当前安装状态。验证器拒绝缺键／重复样本、缺选词、非有限／负数时间、错误客户端或进程代次、内存求和错误及坏计数；全部组成功后才原子写最终报告。

完整 MSVC Release 构建及 5 项相关 CTest 通过：engine_process 约 0.28 秒、engine_host 0.08 秒、engine_host_process 6.52 秒、engine_ipc_benchmark 12.95 秒、engine_host_full 14.10 秒。共注册 44 项，其余既有测试未重复。新增测量测试用微型基础＋完整 FF14 跑 18 组、1,344 个逐键样本、231 次选择和 42 个客户端，检查源文件不变与坏报告拒绝；端点测试确认交接句柄不可继承且不能终止引擎。

### 结果与下一步

四客户端 FF14 组，shared 为 183.43 MiB，相比 local 的 693.73 MiB 减少约 73.6%，相比 isolated 的 699.14 MiB 减少约 73.8%。shared 同轮分项约为协调器 0.97、客户端合计 3.70、宿主 178.76 MiB。两个客户端的 FF14 总量相对 local 减少约 47.9%；一个客户端的 shared 没有内存优势。仅说明本实验快照和这组请求的私有提交量变化，不能套用到此前 1.37 GiB 的真实服务切换测量或实际应用。

四客户端 FF14 的 shared 请求中位／最大为 7.73／124.69 ms，isolated 为 2.32／69.91 ms，local 为 2.22／62.43 ms。shared 工作墙钟约 2,073.72 ms，isolated 约 1,020.66 ms；每个共享宿主只有 2 个工作线程，独占组共 8 个。最慢 shared 请求是 tejihuifuyao 的第 11 键；该输入全部前缀合并中位约 27.30 ms，说明长前缀仍需单独跟踪。本批没有服务端排队／执行分段计时，不能仅凭往返数据把差值全部归为队列或某个搜索函数。

四客户端共享组的全员工作区间共同重叠，基础约 558.65 ms、FF14 约 1,812.18 ms；全矩阵最大的客户端唤醒时间差约 0.097 ms。确实使用了不同客户端进程参与竞争，但仍是固定文本驱动，不等于多个人工应用同时输入。最大单轮内存读取约 0.064 ms，实际采样次数与三个阶段的分项保留在报告中，不能据此保证采样捕获所有短暂峰值。

下一批优先补服务端排队／执行时长，比较 2／4 工作线程和长短请求混合负载，在同等条件下确认延迟及额外内存，再决定线程与超时预算。之后推进共享所有者寿命、可信服务发现／正式诊断和组字边界更新，最后接 TSF、候选渲染和真实应用验收。当前安装未修改，尚未默认启用共享引擎。

## 可选服务计时与混合负载

开发宿主新增 `--threads 1..16`（默认仍为 2）和 `--trace` 绝对文件路径。EngineProcess 的 Config 传递这两个选项。计时默认关闭，不调用额外计时时钟、不分配追踪缓冲区、不写计时文件；Completion 结构保留可选时间字段。开启时预分配 8,192 条固定记录，只保存端点、完整请求身份和单调纳秒时间，无输入／候选文字、路径或异常详情。Host 所属线程写入内存，正常收尾后才统一写 JSONL；文件用 CREATE_NEW 打开，已有文件拒绝覆盖。缓冲区满时不影响候选回复，但计数 dropped，测量验证器会拒绝该组。异常结束可能只留下空文件或不完整记录，不能作为成功报告。

每个成功存入原连接回复队列的 Key 记录六个时间点；取消、迟到、失败和关闭时回收的结果不作为成功计时。时间字段只在同一宿主内相减，不比较不同进程时钟的绝对值：

| 分段 ms | 时间差 | 包含范围 |
| --- | --- | --- |
| queue | started − submitted | 提交后等待工作线程，含线程唤醒和取任务 |
| execution | finished − started | 真实完整查询、候选载荷复验和截止时间检查 |
| publication | published − finished | 等待结果锁、存入结果槽 |
| mailbox | taken − published | 发布后等待所属线程领取 |
| owner | enqueued − taken | 查找原任务、ServerConnection 完成校验／编码及存入回复队列 |
| total | enqueued − submitted | 上述五段之和，不包括写入管道完成 |
| remainder | request_ms − total | 提交前接收／业务处理、编码、管道、排队后发送、客户端校验和其他未覆盖部分；不是纯 IPC 时间 |

客户端逐键记录完整 engine／connection／session／composition／request，验证器再用 engine_index＋endpoint 联合匹配，不用相同数字身份跨连接猜测归属。必须每键恰有一条服务记录、每宿主恰有一条状态，记录数一致、dropped=0、时间单调且服务总时长不超出客户端往返（允许输出精度 0.001 ms）。原始报告保留全部时间点；汇总按各键先计算分段，再分别求中位／最大／合计，不能相加各段中位或最大来代替总时长。

`--workloads uniform mixed` 扩展两类负载。uniform 保留所有客户端相同词序。mixed 让客户端 0 只打长词，其他客户端只打其余词：基础长词为 xinkule，FF14 为 tejihuifuyao。四客户端每轮基础 mixed 为 64 键／13 次选择，FF14 为 90 键／16 次选择；长短任务数量不同，完成后客户端不会继续补发，不能认为整个工作区间始终有四个活跃请求。汇总另列 long／short 两组；uniform 也用同样词组划分，方便对照。1 客户端 mixed 只有长词，不构成竞争。

同一份完整词库比较 2／4 工作线程：

```powershell
python -X utf8 scripts/benchmark-engine-ipc.py --reader .build/windows/msvc/Release/harukoto_engine_ipc_benchmark.exe --host .build/windows/msvc/Release/harukoto_engine_host.exe --lexicon .build/windows/ime --counts 4 --modes shared --threads 2 4 --profile --workloads uniform mixed --runs 3 --output .build/windows/engine-ipc-thread-profile.json
```

省略 `--profile` 可生成同配置的无计时对照；local 总是 threads=0／profile=false，多线程列表不会重复运行 local。格式 2 中组身份是 scenario／mode／clients／threads／profile／workload。运行顺序为基础／FF14、人数、模式、线程数、负载；仍是固定顺序和未控制缓存／其他系统负载的实验，计时时钟、缓冲区和内存采样也有成本。不得把一次开关计时差值解释为精确探针开销，或用单组最大值当分位数保证。

回归保留默认 18 组、1,344 键／231 次选择；新增微型基础＋完整 FF14 的 20 组线程／负载矩阵（local 只执行一次线程配置），2,050 键，其中 1,640 键与服务时间逐一对应。覆盖 2／4 线程、共享／独占端点归属、缺失／重复／错代次／反向时间／丢记录／超出往返时间拒绝，并检查分段合计。执行器用受控计时验证正常与取消／停止时间，真实宿主回归验证追踪路径已存在时启动失败且词库未变。
